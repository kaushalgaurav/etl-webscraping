ETL Platform Code Map

Every folder and file in the backend, explained in plain language: what it is for, what is inside it, and how it connects to the rest. The project collects Indian health and population data (Census 2011, HMIS, data.gov.in), cleans it, combines it and calculates indicators from it.

How data moves through the code

  1. FetchCensus API, HMIS site, data.gov.in, files, web pagesby ingestion/ and connectors/
  2. Store rawrawcensus_raw
    hmis_raw
    ds_<id>    exactly as received
  3. Cleancleancensus_clean
    hmis_clean    by cleaning/
  4. Finalizemastercensus_master
    hmis_master    one row per place, newest wins
  5. Mergeoutputdashboard_masterby merging/
  6. MeasureoutputKPIs, CSV, PDFby kpi/ and reports/

Slow steps (fetching, merging) run as background jobs in jobs/. Answers from Google Gemini follow their own path in ai_data/ and are stored in separate gemini_* tables that never mix with the official data.

Two ways data is stored

Its own table per fetch

Simple sources (a data.gov.in resource, a CSV, a web page table) each get a new table named ds_<id>. A row in the datasets table describes it. A cleaned copy gets its own new table and its own datasets row, linked back to the original.

Shared stage tables

Census and HMIS go into shared tables, one per stage (census_raw, census_clean, census_master, and the same for HMIS). Every row is stamped with the fetch it came from, the time, and its survey_id. Fetching again under the same survey_id replaces that survey's rows.

File names you'll see in every module

router.py
The web addresses (endpoints) the module answers, such as POST /ingest/fetch. It checks the request and hands the work to the service.
service.py
The actual work: fetching, cleaning, joining, calculating.
schemas.py
With an s. The shape of requests and replies: which fields a request may send and what comes back.
schema.py
Without an s. The shape of the warehouse tables: table names and which columns identify a row.
__init__.py
Marks a folder as a Python package. Almost all are empty.

Follow one request from start to finish

  1. You send POST /ingest/fetch with a Census URL and survey_id: 1.ingestion/router.py
  2. The request is checked against FetchRequest, a job is queued, and you get a job id back at once (status 202). You check progress with GET /jobs/{id}.ingestion/schemas.py · jobs/service.py
  3. A worker thread picks up the job and calls run_fetch(), which sees the host censusindia.gov.in and takes the Census path.ingestion/service.py
  4. The Census connector calls the Census API page by page. Each chunk is added to census_raw, stamped with survey 1.connectors/census_india.py · crud/dataset.py
  5. You call POST /warehouse/census/rebuild?survey_id=1. It cleans census_raw into census_clean, then keeps one row per place in census_master.warehouse/router.py · census_warehouse/service.py
  6. After fetching HMIS the same way, POST /datasets/merge joins census_master and hmis_master for survey 1 into dashboard_master.merging/run.py · merging/survey.py
  7. GET /kpi/dashboard?survey_id=1 calculates the 28 dashboard cards, counting each district's population only once.kpi/indicators.py · kpi/aggregation.py
No file matches that search. Try a table name (hmis_master), a function (build_master) or a word like "district".

app/ top level

The front door. These files start the server and plug every module's web addresses into one app. They hold almost no logic of their own.

main.py

Start here37 lines

Starts the server. It creates the FastAPI app, lets browsers call it from any website (CORS, fine for local use but to be tightened before going live), plugs in all routes, and adds a GET /health check. On start it runs init_db(); on stop it shuts down the background job workers. root_path="/etl" is there because the live server sits behind a proxy under /etl.

# runs when the server starts (before yield) and stops (after)
@asynccontextmanager
async def lifespan(app: FastAPI):
    init_db()
    yield
    shutdown_jobs()

app = FastAPI(title="Data Ingestion & Analytics Platform", version="0.2.0",
              lifespan=lifespan, root_path="/etl")

schemas.py

23 lines

Reply shapes used by more than one module. It holds DatasetOut, the description of a dataset sent back to the client: id, name, stage, connector, source, row and column counts, parent datasets, notes, error and creation time. Shapes used by only one module live in that module's own schemas.py.

app/db/

The database connection and what happens on first start.

base.py

6 lines

The parent class every table model inherits from (SQLAlchemy's DeclarativeBase). Alembic reads it to learn which tables the code expects to exist.

session.py

37 lines

Creates the database connection (engine) and a factory for sessions (SessionLocal). For SQLite it allows use from several threads and waits up to 30 seconds when the file is busy, because jobs and web requests write at the same time. For PostgreSQL it checks a connection is still alive before using it, since long jobs otherwise hit connections the server has closed. get_db() gives each web request its own session and closes it afterwards.

init_db.py

51 lines

Runs once when the server starts. It loads the list of data sources from seed_sources.json into the sources table, skipping ones already there, and marks any job still "running" from a previous server run as failed. It also has run_migrations(), but that call is commented out, so tables are never created automatically. You run alembic upgrade head yourself.

def init_db() -> None:
    #run_migrations()
    ...
    db = SessionLocal()
    try:
        seed_sources(db)
        orphaned = reap_orphaned_jobs(db)

state_aliases.py

60 lines

The official spelling of each state and union territory: "Orissa" becomes Odisha, "NCT of Delhi" becomes Delhi, "Pondicherry" becomes Puducherry. Without it, joins between sources silently miss rows. Copied from the older ETL so both agree.

canonical_fields.py

45 lines

The dictionary of column names that mean the same thing, for example unique_id = district_unique_id = area_id. The merge code uses it to find the join column in each table. It also sets how close a fuzzy match must be: 0.72 against a known name, 0.6 between two raw names, with that second kind capped at 0.8 confidence. To teach it a new alias, add it to the dictionary.

hmis_indicators.py + .tsv

50 lines + 198 indicators

HMIS reports name indicators in long sentences that change punctuation from year to year. This maps each one to a short code, its programme and its grouping. lookup(label) matches on a cleaned-up version of the label, so "Sterlisation" and "Sterilisation" still match.

kpi_catalog.py + .tsv

288 lines + 227 indicators

The 227 indicators of the report template (General_Population_Template.xlsx) in 8 themes: RMNCH 41, NCDs 35, Socio-economic 32, Communicable diseases 31, HRH 24, Demographic 24, Infrastructure 22, Nutrition 18. detector.py

183 lines

Decides how to read a URL. It tries the most reliable method first and never starts with a browser:

  1. Official API (known hosts censusindia.gov.in, api.data.gov.in)
  2. Downloadable CSV or Excel
  3. Raw JSON or XML
  4. HTML table on the page
  5. JavaScript-rendered page

A page that links to a CSV counts as a file source. detect_connector() makes the choice; probe_url() reports what is actually available.

aggregation.py

Start here84 lines

The one adding-up rule every KPI follows. After the merge, a district's Census population is repeated on each of its HMIS rows, one per reporting period. Adding it up naively counted each district many times and gave India a population of about 4.4 billion instead of 1,210,854,977. The fix: a column ending _census is summed over one row per district; an HMIS column over all rows.

def one_row_per_place(df):
    for key in PLACE_KEYS:   # unique_id, district_id_census, district_name_census
        if key in df.columns:
            return df.drop_duplicates(subset=[key])
    return df

def frame_for(df, column):
    return one_row_per_place(df) if is_census(column) else df

total() and ratio() use this to add up and divide; note() writes a short explanation of how each value was reached.

gemini.py

Uses Gemini217 lines

Talks to the Gemini API over plain HTTP. Google Search grounding is on, so Gemini can look figures up and report which pages it used. It stays within GEMINI_RPM calls per minute, retries on errors 429, 500 and 503 using Google's suggested wait, and doesn't retry when a daily quota is used up. parse_table() pulls the JSON table out of the reply even if Gemini wrapped it in extra text.

store.py

409 lines

The four Gemini tables: gemini_fetches (one row per prompt), gemini_raw (each value as returned), gemini_clean and gemini_master. Values are stored one per row, because twenty prompts could name over a thousand columns and PostgreSQL allows at most 1,600 per table. It recognises state, district and year columns, matches place names to the district master, and wide() lays values back out as a normal table for viewing.

Heads-up. Alembic's skip list doesn't include gemini_ tables. An auto-generated migration would try to drop them, so always check generated migrations.
