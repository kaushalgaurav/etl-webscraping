Data Platform Redesign and the "Website" Tab

ETL service (platform/backend) · Draft for tech lead review · 4 November 2026
In short
  • Today, only Census and HMIS data reach the dashboard. Uploads and other links each create a new database table that is never used again and never deleted.
  • The cause is the storage design: four different ways of storing data, each number copied up to four times, and new tables created on the fly.
  • The proposal: store every number from every source as one row in one shared table (observations), with small reference lists for places, indicators and surveys. No table is ever created per import.
  • The new Website tab lets an admin enter any web address, see the tables and files found there, pick what to keep, match it to places and indicators, and save it into the same shared table. Everything not picked is thrown away.
  • Rollout is phased: new tables and the Website tab first; Census/HMIS move across only after every KPI number is verified to match.

1. How it works today

The admin works in the nimbli.ai portal. The portal's own backend (built by another team) sends requests to this ETL service, which stores data in PostgreSQL. Long tasks run as background jobs: the service replies at once with a job number (HTTP 202), at most two jobs run at a time, and the portal checks the job until it finishes.

1.3 Gemini (AI) data

An admin can ask Gemini for a table in plain words. The answer is stored in Gemini's own four tables (gemini_fetches / raw / clean / master), already as one row per number, and is deliberately kept apart from official data. It does not create ds_ tables and does not feed the KPIs. This stays as it is.

2. Problems with the current design

ProblemWhat it means in practice
1. Four storage shapesCensus is wide (one column per figure, ~93 columns), HMIS is read as rows then folded wide (~94 columns), Gemini is one row per number, everything else gets its own table. Every new kind of source needs its own storage and merge code.
2. A new table per importEach upload or non-Census/HMIS link creates 1–2 ds_ tables. Re-fetching the same link adds two more. Nothing ever deletes them, and there is no delete endpoint.
3. Same number stored up to 4 timesRaw, clean, master, then again in dashboard_master. This is the main storage cost.
4. Double counting riskCensus has one row per district; HMIS has one per district per period. The merge repeats each Census value on every HMIS row, so a plain sum is wrong. This once gave an all-India population of 4.4 billion (true value 1,210,854,977). Every KPI must now go through special guard code.
5. Only Census/HMIS reach the dashboardThe merge only knows those two. Uploads, other links and a future Website tab can be viewed and exported, but never appear in KPIs.
6. Key reference data is not in the databaseNo list of surveys (a survey is just a number anyone types). Places live in a TSV file. An indicator is just a column name: no label, no unit, no rule for whether it can be added up.
7. Wide tables hit limitsOne HMIS report year once produced 1,257 columns; PostgreSQL allows at most 1,600 per table.
8. No way to read an arbitrary websiteOnly plain HTML tables and direct file links work. The JavaScript-page connector is an empty stub.

Also seen (portal side, for the portal team): Save receives a successful 202 response, but the page shows "Network error, please try again".

3. Proposed design

3.1 The core idea: one row per number

Every number, from any source, answers the same four questions: which place, what is measured, which period, what value. Those become fixed columns. A new kind of figure becomes a new entry in the indicators list, never a new column or table. This is how any website table fits a fixed schema.

3.4 Rules

  • One value per survey + place + indicator + period. Saving the same figure again replaces it, so nothing is double-stored. If a save would overwrite figures that came from a different source (e.g. website population over Census population), the admin is warned first.
  • Raw files are not stored. Data is cleaned in memory during the save; only the final numbers are written. The file's address, time and fingerprint are recorded.
  • Only what the admin picks is stored. Website findings are held temporarily and deleted on Save, or after 24 hours if nobody saves.
  • Indicators are created on the spot by the admin while saving. The system first suggests close existing matches to avoid near-duplicates.
  • Periods carry their meaning. HMIS values are cumulative year-to-date ("up to June", "up to September"…), so they must never be summed across periods. Each indicator's total rule and each period's start/end date prevent this.

3.5 Growth and speed

What is loaded (per survey)Rows in observations
Census, district level (640 districts × ~80 figures)~51,000
HMIS, district level (640 × ~90 figures × 4 periods × 2 years)~460,000
Census, village level (~600,000 villages × ~80 figures)~48 million (a few GB)
  • Partitioned by survey: each survey's rows are kept separately, so reading one survey never scans others, and deleting a survey is instant. (PostgreSQL 11 or newer.)
  • Indexes on place, indicator and period for fast lookups.
  • A pre-built dashboard summary (materialized view), refreshed after each save. It keeps today's dashboard_master column names, so existing KPI formulas keep working.
  • Archiving: unused surveys can later be exported to S3 and removed from the database.

Honest trade-off: one stored number takes slightly more space as a row than as a cell in a wide table. The saving comes from storing each number once (not four times) and from no longer creating tables per import.

4. The Website tab

4.1 What the admin does

1. Enter URL, click Search
→
2. System finds tables and files
→
3. Tick what to keep
→
4. Match places and indicators
→
5. Save

Uploads and other links skip steps 1–2 and use the same review, match and save steps, so they reach the dashboard too.

Review screen (built by the portal team): for each table found, the admin sees its title, size and a preview, plus hints such as "looks like page layout, not data". For each ticked table:

ItemWhat happens
Place columnDetected automatically and matched against places, e.g. "36 of 38 districts matched, 2 unmatched (view)". If there is no state column, the admin picks the state.
Each figure columnSuggested match to an existing indicator ("Total Beds" → Hospital beds), or "+ New" with name, unit and total rule. Text columns are skipped.
PeriodTaken from a year column if present, otherwise typed by the admin.
No place columnSaved as a loose table (not on the dashboard).
Special shapesMany rows per district (e.g. a hospital list): "add up per district" or "count per district". Years as columns: marked as periods. Male/Female columns: folded into the indicator name.

4.2 How Search works

  1. Safety check. Only public web addresses are allowed; internal addresses (the server's own network, cloud metadata) are blocked. The site's robots.txt is respected.
  2. Plain download first. The page is downloaded and searched for HTML tables, data embedded in the page, and links to files (CSV, Excel, JSON, PDF, Word, ZIP).
  3. Browser only when needed (phase 3). If the page builds its tables with JavaScript, a headless Chromium browser loads it and also captures the data the page fetches in the background, including further pages of results.
  4. Files are read: spreadsheets per sheet, tables from PDF and Word, files inside ZIPs.
  5. Blocks are reported, not bypassed: login required, captcha, bot protection, robots.txt refusal, too large, timeout. These appear under "Couldn't read".
  6. Hints help the admin decide: layout tables, duplicates, mostly-numeric tables, how many places match, possible personal data (never pre-ticked).

Limits my call, configurable: 180 seconds per Search, 1 request per second per site, 25 files, 30 MB per file, 200 MB per Search. The bot identifies itself honestly as NimbliDataBot/1.0.

6. Risks

RiskHow it is handled
KPI numbers change during the switchOld and new run side by side; switch only when every number matches.
Place names don't matchAdmin sees unmatched names before saving; confirmed spellings are remembered.
Near-duplicate indicatorsSuggestions shown before creating a new one; a merge tool can follow.
Websites block us or changeBlocks are shown, never bypassed. Re-running a Search and saving again replaces the earlier values.
Security of fetching any URLInternal addresses blocked, including for the browser; downloaded files never executed.
Table size at village levelPartitioning, indexes, dashboard summary, archiving.

7. Decisions and open questions

Decided

  • Store only what the admin picks; original files are not kept.
  • Census and HMIS move to the new design, in phases.
  • All place levels are supported, down to village and ward.
  • Tables without places are kept as loose tables, not on the dashboard.
  • Uploads and other links use the same flow as the Website tab.
  • Admins create new indicators on the spot.
  • The portal screens and backend are built by the portal team against the contract in 4.3.
  • Gemini data stays separate.
